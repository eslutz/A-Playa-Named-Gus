# API-key release without interactive sign-in

The October 25, 2026 Seerr release established a native Xcode CLI path using the existing team API key. Xcode Cloud starts also work with corrected authentication, but Cloud runs 29/30 and routine diagnostic run 31 failed before creating any actions. Their startup cause remains unknown. They do not constitute successful Cloud qualification.

## Authentication

Keep the existing read-only inspection helper's GET scopes. For deliberate API writes, use a short-lived ES256 JWT **without the optional `scope` claim**. A token scoped to `POST /v1/ciBuildRuns` returned HTTP 405; the otherwise identical request without scope created a run. Apple documents scopes using GET requests and allows unscoped tokens for operations permitted by the key's role: [token documentation](https://developer.apple.com/documentation/appstoreconnectapi/generating-tokens-for-api-requests).

A build-start response can initially contain an empty source SHA. Read the created run again and verify the intended full merge SHA. After an ambiguous start or upload, inspect existing runs/upload states before retrying.

## Local Xcode delivery

The owner requested an alternate delivery method after Cloud startup failed. For this release, all 13 required GitHub checks passed on a source tree identical to merged main. The four native Release archives were then rebuilt, scanned using the existing strict diagnostic gate and verified for Apple Silicon and signatures before distribution. Default Cloud delivery policy remains the default for subsequent releases; this record does not claim a successful Cloud run.

1. Choose a build number unused by every native platform; check both uploaded builds and product-wide Cloud runs. Use identical versions on the app, Watch and Top Shelf. The Seerr artifacts use **1.0.0 (31)**. Cloud diagnostic run 31 also completed, so the next Cloud run should be 32; verify the server's run number rather than assuming it.
2. Archive from the checked source with the normal architecture/warning settings. This project's shared configuration defaults to manual ad-hoc signing. Local device archives instead used `CODE_SIGN_STYLE=Automatic`, `CODE_SIGN_IDENTITY=Apple Development`, `DEVELOPMENT_TEAM=QS3GC3CT43`, and the existing API key with `-allowProvisioningUpdates`, `-authenticationKeyPath`, `-authenticationKeyID`, and `-authenticationKeyIssuerID`. The explicit team also applies to package resource bundles. Keep the Watch automation layout override and Intel exclusions from the shared build wrapper.
3. Export/upload with `method=app-store-connect`, `signingStyle=manual`, explicit distribution certificate/profile mappings, `testFlightInternalTestingOnly=true`, `manageAppVersionAndBuildNumber=false`, and `uploadSymbols=true`. Use `destination=export` for a reviewable package and `destination=upload` for delivery. Native macOS additionally requires the explicit installer certificate.
4. Put `/usr/bin:/bin:/usr/sbin:/sbin` first in Xcode's process `PATH`. On this Mac, Apple's rsync launched Homebrew rsync 3.5.1 as its peer, which rejected Apple's `--extended-attributes` option and caused `exportArchive Copy failed`. Using system tools first fixed packaging; no app source or diagnostics were changed.
5. Verify the exported Mac package's nested resource bundles. Xcode retained a development signature on `Contents/Resources/swift-nio_NIOPosix.bundle`, and Apple rejected it with code 90284. The release artifact's resource bundle was re-signed with the distribution identity, its outer archive seal restored while preserving entitlements, then re-exported. Verification of the actual package required a valid installer signature, arm64 executable, valid complete app signature and the same certificate on app/resource bundle and App Store profile. No entitlements or source files were removed to make signing pass.
6. Inspect `GET /v1/apps/{id}/buildUploads` for server processing errors/warnings, then require native `preReleaseVersion.platform`, `processingState=VALID`, `buildAudienceType=INTERNAL_ONLY`, and beta readiness. Successful delivery alone does not establish a processed build. Update tester notes using the beta localization **`whatsNew`** field. Add the four validated native builds to Gus Internal and read back each group's association and internal beta state.

The original local distribution key triggered a macOS SecurityAgent authorization request. Its access controls were preserved. Separate app-distribution and Mac-installer keys/certificates were created via the API and installed into a dedicated Keychain, with access for the required Apple signing tools. The Keychain, private unlock material and explicit per-platform export mappings are retained outside Git under `~/.appstoreconnect/signing/gus-cli-2026-10-25/` (directory 0700, credential files 0600). Temporary raw private-key/PKCS#12 copies were removed after a signature probe verified the persisted Keychain. No existing certificate was revoked.

This directory contains credentials: never attach it to a PR, report, or handoff. The task-local build driver and private logs remain under `/tmp/gus-seerr-local-release/`; the source-controlled [release evidence](../Reviews/README.md) contains only sanitized metadata and hashes.
