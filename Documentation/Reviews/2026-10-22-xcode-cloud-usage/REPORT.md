# Xcode Cloud usage diagnosis — October 22, 2026

Read-only audit of live Apple API workflows and run/action history, selected downloaded raw logs, repository CI scripts, and the supplied October 12 usage screenshot. No workflow or source settings changed. Action elapsed spans are not billed usage: they include orchestration and potentially waiting. Exact quota amounts below come from the screenshot, not sums of API action spans.

## Findings

1. **Usage is additive across parallel workers.** The screenshot totals 6h 14m 08s: Gus 4h 23m 42s and PumpSync 1h 50m 26s. Gus build 13 elapsed 12m 20s but used 43m 03s; PumpSync build 47 elapsed 11m 27s but used 40m 38s. The screenshot is a partial view: live history contains additional PumpSync runs 41–46 and 48 on October 12 not shown there.
2. **PumpSync runs its full test scheme on four phones.** Build 47 artifacts and test results identify iPhone SE (3rd generation), iPhone 16, iPhone 16 Pro, and iPhone 16 Pro Max. Each runs 387 unit tests (about 26–27 seconds) and 19 UI tests (about six minutes). The four test-without-building commands last about 7m 17s–7m 27s each. Build-for-testing compilation lasted 18 seconds; post-clone Homebrew/XcodeGen preparation lasted nine seconds. UI automation and simulator overhead, multiplied across devices, dominate this sample.
3. **Gus performs eight substantial jobs per release.** Current configuration has four platform test actions and four archives, plus four brief TestFlight post-actions. iOS selects iPhone and iPad; recommended Apple TVs previously produced two destinations. Build 28 elapsed 15m 22s; test action spans were 8.1–11.4 minutes and archive spans 5.7–10.6 minutes. Those overlapping spans must not be added and called billed usage. TestFlight post-action spans total less than a minute.
4. **Failed attempts continue consuming archive work.** Of the Gus runs visible in the screenshot, failed/canceled builds 7, 9, 10, 11, and 12 used 2h 38m 21s, about 60% of visible Gus usage. Build 12 failed iOS testing after 1.28 minutes, but all four archives still succeeded; its Mac archive action lasted 16.64 minutes. PumpSync build 40 failed a UI assertion at PumpSyncUITests.swift:209: 43.999999999999986 was compared against a strict minimum of 44.0. Its archive succeeded but distribution was skipped. Current source status of that historical assertion was not assessed.
5. **Both release workflows force clean builds.** Live clean=true prevents cached build-data reuse. It is a plausible recurring cost, especially for Gus dependencies, but the savings require a measured comparison. PumpSync build 47 compiled rapidly, so caching alone will not solve its dominant UI cost.
6. **Some long elapsed times are infrastructure/orchestration delays.** Gus build 19 Mac archive action lasted 55m 45s. Its first package-resolution log starts at 18:52:38 UTC, compilation runs 18:53:10–18:54:57, and exports finish by 18:55:08. Run began 18:09:51 UTC. Most elapsed delay preceded package/build commands. Logs do not establish the precise infrastructure cause or which waiting portions were billed. Build 27 also had a 30.46-minute failed tvOS action; the API issue list was empty, so its failure cause remains unproven.
7. **Existing controls already help.** Gus currently has exact-main triggers, build-input file filters, auto-cancel, and no schedule or PR trigger; the older validation workflow is deleted. PumpSync currently has no automatic branch/PR/schedule trigger; inspected runs are manual. Disabling additional automatic PumpSync triggers would not address this history.

## Recommended changes, in order

- Use the existing PR CI gate for iteration and run the full Cloud release matrix only for selected release candidates. Changing Gus automatic merged-main release behavior would change the recorded delivery policy and needs an explicit decision.
- For PumpSync, run unit tests plus a focused UI smoke suite on one representative iPhone for routine candidates. Run the full UI/device matrix for release qualification or on a deliberate cadence. This trades some per-candidate device coverage for lower compute use; three fewer copies of a six-minute suite avoids roughly 18 minutes of UI execution alone in the build-47 sample, before simulator overhead. It is not an exact billing forecast.
- Trial cached builds for internal workflows, retaining deliberate clean release validation when needed. Compare actual Apple usage over multiple comparable runs before promising savings.
- Resolve reproducible test failures before another complete release attempt; where practical validate the failing lane first. Merely requiring tests gates distribution, not parallel archive execution.
- Keep all required platform coverage on full Gus release candidates. Removing a platform is a product/release-scope decision, not a free performance improvement.
