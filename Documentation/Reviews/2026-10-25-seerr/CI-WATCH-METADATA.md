# Deterministic Watch metadata extraction in automation

The first PR #34 iOS build compiled successfully but the strict warning gate rejected `Metadata extraction skipped, no AppIntents.framework dependency found` from the embedded `GusWatch` target. [Failed job](https://github.com/eslutz/A-Playa-Named-Gus/actions/runs/40200064820/job/121189166830). The iPad and standalone Watch builds passed; no warning waiver or scanner change was made.

The framework was already an explicit dependency. The failed log shows the Watch code dylib linking AppIntents, then the generated preview dylib writing the same linker-dependency file without it. Metadata extraction subsequently consumes that shared file. Local inspection likewise finds AppIntents in the code dylib but not the preview dylib or executor stub. This is consistent with link-order-dependent dependency metadata, rather than a missing project framework declaration.

Apple documents a per-target ordinary executable layout for tooling that cannot handle the debug-dylib layout. GusWatch Debug now reads `ENABLE_DEBUG_DYLIB` from `GUS_WATCH_DEBUG_DYLIB`, which defaults to YES for local Xcode development. The warning-free automation wrapper and Cloud post-clone override select NO. Other app targets retain their layout; Watch Release retains its existing ordinary executable layout. Local Watch previews remain enabled. [Apple's layout documentation](https://developer.apple.com/documentation/xcode/understanding-build-product-layout-changes).

The generated Cloud configuration regression and command-wrapper regression failed before the correction and now pass (19 bootstrap tests and 11 warning-gate tests). Native build-setting assertions confirm local Watch Debug YES, automated Watch Debug NO, and Watch Release NO. A CI-style Watch build and the embedded iOS build pass with zero diagnostics. The resulting Watch executable directly links AppIntents and its dependency metadata contains that framework. Metadata extraction and all diagnostic rejection rules remain enabled.
